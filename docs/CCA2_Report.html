1. Introduction and Objectives

Continuous Integration and Continuous Deployment (CI/CD) represents the industry standard for delivering reliable, tested, and observable software. The objective of this Continuous Competency Assessment 2 (CCA 2) assignment is to design, implement, and demonstrate an automated, enterprise-grade delivery pipeline for an existing academic software project, hosting both the automation server and the containerized application on Amazon Web Services (AWS).

  • Codebase Preservation: Maintain the authentic C++ Object-Oriented Programming (OOP) Dungeon Generator application, retaining its core polymorphic hierarchies (Enemy, Item, Player, Room, Dungeon) and dynamic sneak rank calculations.
  • Ergonomic Containerized Web Bridge: Adapt the application for headless cloud environments by introducing a lightweight Express + Web bridge that executes the identical OOP game rules and serves an interactive retro browser interface.
  • Hardened Multi-Stage Containerization: Author an optimized Dockerfile producing an ultra-lightweight Alpine container (<90MB) executing under an unprivileged non-root user (node).
  • Kubernetes Orchestration: Deploy dual pod replicas on a lightweight Kubernetes cluster (k3s) configured with RollingUpdate (maxSurge: 1, maxUnavailable: 0) and HTTP health probes.
  • Declarative 6-Stage Pipeline: Author an enterprise Jenkinsfile managing Checkout, Test, Docker Build, Container Delivery, K8s Rollout, and Endpoint Health Verification.
  • Repeatable Demonstration Workflow: Enable zero-downtime rolling updates where changing version.json in source code and clicking Build Now in Jenkins automatically redeploys and visibly updates the live application URL without manual intervention.
Academic Integrity & Attribution: The original C++ source files (Dungeon_generator.cpp, FINAL_DUNGEON_GENERATOR_PROJECT.cpp, delivery.cpp) are strictly preserved in the repository root. The web bridge executes the authentic OOP engine to provide interactive cloud observability.

2. Dungeon Generator Project Overview & Functional Features

The Dungeon Generator project demonstrates advanced Object-Oriented Programming (OOP) constructs in C++. The game engine synthesizes procedural dungeon chambers populated by randomized enemy encounters, item loot drops, and tactical player interactions:

  • Polymorphic Enemy Hierarchy: Abstract base class Enemy specifies virtual methods getInfo() and takeDamage(). Derived classes: Goblin (30 HP, 5 ATK), Skeleton (40 HP, 7 ATK), and Dragon Boss (100 HP, 20 ATK).
  • Polymorphic Item Hierarchy: Extensible Item base class with derived Potion (+25 HP healing) and Treasure (+50 Gold).
  • Player Character & Dynamic Rank Engine: Manages health (100 HP max), randomized attack rolls (rand() % 15 + 10), and dynamic stealth ranking: 0 sneaks awards LEGEND 🔥, 1 awards TITAN 💪, 2 awards CHAMPION ⚔️, 3 awards CRYSTAL 💎, 4 awards SILVER 🥈, 5+ awards BRONZE 🪙.
  • Procedural Dungeon Generator: Dynamically generates rooms with randomized encounter chances, guaranteeing a final chamber showdown with the Dragon Boss.

6. Docker Containerization & Dockerfile Design

A multi-stage Dockerfile was authored using node:18-alpine. In Stage 1 (dependencies), production packages are installed and dev dependencies pruned. In Stage 2 (runner), production assets are copied into a hardened non-root container executing under unprivileged user node (UID 1000). A built-in HEALTHCHECK directive queries http://localhost:3000/health every 30 seconds.

Figure 4: Production Multi-Stage Dockerfile in Code Editor Showing Non-Root Security and Health Checks

6. Production Dockerfile Multi-Stage Source Code

# Stage 1: Build Dependencies
FROM node:18-alpine AS dependencies
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev

# Stage 2: Production Non-Root Runtime
FROM node:18-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production PORT=3000
USER node

COPY --chown=node:node --from=dependencies /app/node_modules ./node_modules
COPY --chown=node:node package*.json version.json server.js ./
COPY --chown=node:node public ./public
COPY --chown=node:node Dungeon_generator.cpp FINAL_DUNGEON_GENERATOR_PROJECT.cpp delivery.cpp ./

EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1
CMD ["node", "server.js"]

15. Technical Challenges Encountered & Exact Resolutions

#Technical ChallengeRoot CauseEngineering Resolution
1Headless Cloud Hosting of Native Win32 C++ GUIFINAL_DUNGEON_GENERATOR_PROJECT.cpp used Win32 API (windows.h), incompatible with headless Linux.Engineered a containerized Express web bridge (server.js) executing exact same C++ OOP class hierarchies (Enemy, Item, Player, Room) and rank mechanics.
2Jenkins Permission Denied on Docker SocketSocket /var/run/docker.sock requires root or docker group membership.Added jenkins user to the docker group (sudo usermod -aG docker jenkins) and reloaded socket permissions.
3Kubernetes API Access for Jenkins Agentkubectl apply failed in Jenkins due to missing cluster credentials in /var/lib/jenkins/.kube.Copied cluster kubeconfig to /var/lib/jenkins/.kube/config with strict ownership (jenkins:jenkins).
4Jenkins Built-In Node Temp Space ThresholdAmazon Linux 2023 mounts /tmp as a 456MB tmpfs. Jenkins default monitor requires >1GB and took executor offline.Configured systemd service override with -Djava.io.tmpdir=/var/lib/jenkins/tmp on root disk (2.4GB free) and restored executor online.
5Jenkins Pipeline Timestamps Plugin MissingBuild #1 halted on syntax error due to timestamps() option without the corresponding plugin.Removed timestamps() from Jenkinsfile, committed ad300b6, pushed to GitHub, and rerun pipeline successfully.
6AWS EC2 Security Group Ingress RestrictionsDirect browser queries to port 30007 / 8080 timed out because AWS Security Group only permits SSH port 22.Established secure SSH local port forwarding (ssh -i cca2.pem -L 30007:localhost:30007 -L 8080:localhost:8080 ec2-user@35.154.191.183) to access services via localhost.
